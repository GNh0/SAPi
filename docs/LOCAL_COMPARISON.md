# Local comparison prototype

This prototype has no GNho source connection, listener, outbound transport or production database binding. It compares a bounded synthetic semantic envelope against a fixed ordinary dummy handler and the actual JavaScript `SecureServer` with a fixed dummy handler. A request has exactly `correlationId`, `operation`, `identity`, and `data`; other envelope fields and bodies over 8192 bytes are rejected. The adapter returns a transient comparison result to the runner; it does not retain a second result store. Adapter or evidence errors stop the run.

From the repository root on Node 24, choose a new SQLite filename directly inside the fixed workspace `evidence/local-runs` directory; an existing file is never opened or overwritten. Node's `node:sqlite` currently reports an experimental warning.

```sh
node tests/test_local_comparison.mjs
node examples/shadow/run-local.mjs --dry-run
node examples/shadow/run-local.mjs --loopback /absolute/path/to/SApi/evidence/local-runs/new-evidence.sqlite 2
```

The CLI is disabled without an explicit mode. Dry-run only produces the seeded plan; loopback calls both local handlers and writes a new version 3 SQLite evidence file. Each start and result is committed individually. Evidence contains only bounded allowlisted identifiers, enums, counts, timings, hashes of fixed dummy state and code provenance; raw callback records, responses, tokens and dummy state are never persisted. The store recomputes fixed fixture expectations and rejects inconsistent observations or state hashes. Its completed status `fixture_consistent` describes internally consistent synthetic evidence, not verified callback provenance or production behavior. The SHA-256 covers the local runner and JavaScript SDK sources, and the metadata records the available Git HEAD, Node version and fixture version. Git HEAD may not describe uncommitted files; the hash is not a signature or proof of authenticity. The callback target's provenance is explicitly unverified. If the process stops abruptly, status remains `running` and the started events without a result, or plan entries without a start, need reconciliation. `readEvidenceSummary` identifies versions 1, 2 and 3 and returns only counts; it does not expose earlier raw events. Existing databases are not migrated or modified, and version 1 files may contain raw callback data.

New runs also require the exact seeded fixture order, with each group containing all four fixtures. The summary reader does not revalidate older version 3 plans, so prior `fixture_consistent` records must not be assumed to have passed this later check.

A run is finite (1–7 sets of four fixtures, at most 28 observations), one in flight, at least one second between observations, with a stop signal and omitted/error records. The optional last CLI argument selects the number of sets and defaults to one. The seed determines fixture ordering. Each set starts with an independently empty expected and dummy state, and evidence events carry a zero-based group number. Expected response `ok`, reason, shape, data and before/after states are checked. Matching two wrong states is not a pass.

The loopback CLI runs each observation in a separate local child process with ignored standard streams. The child accepts only a seed, a fixed fixture index and a local test mode; it receives no SQLite path. It reconstructs prior dummy state within the same set by replaying earlier fixtures in that child, writes a bounded allowlisted result to a temporary file, then atomically renames it. The parent reads it only after a successful child exit. Temporary run directories are restricted to `evidence/local-runs`; the parent removes only the known files and directory after child exit. This replay means each four-observation set performs ten total dummy SDK calls.

When the CLI threshold is exceeded, only a kill request followed by a signalled child exit is recorded as `timeout_child_terminated`. A child that has not started, already exited, or completed after the elapsed deadline is recorded separately. Evidence includes the target sequence and PID where available, kill-request and exit-observation flags, and whether exit was normal. Only the fixed process adapter is recognized for those claims; a caller-supplied termination function cannot make them. If termination cannot be confirmed, the run is left incomplete rather than marked as passed. A local test blocks the child, checks that it started, terminates it, and verifies no later SQLite or run-directory write. The parent event loop and OS scheduling can delay timeout handling, and a child process is not an OS security sandbox. The general `runMixed` API still permits an in-process callback: that mode cannot interrupt synchronous work and records `timeout_unknown`; a timed-out callback can continue with later side effects. This is local dummy-only tooling, not an authorization to run against an external service or a production Worker.

The artifact-path check examines the workspace directory and its `evidence/local-runs` descendants, rejecting links at those levels and checking their canonical locations. It does not inspect ancestors above the workspace, and the filesystem can change between a check and a subsequent operation. It is not a defense against a hostile local user or concurrent path substitution.

The in-memory replay store is scoped to one process and is not a cross-isolate guarantee. `atomic-replay-contract.mjs` is an interface adapter, not a D1 implementation. A future backend must atomically claim a replay ID and atomically evaluate and update all applicable admission limits across instances, return a strict boolean, and fail closed on errors. The local concurrency test uses a shared in-memory fake and actual SDK calls; it does not establish D1 transactions, consistency, migration or durability. No production schema is created or changed.

The ordinary handler implements only the same fixed dummy operation and policy for these fixtures. This is not full normal-function parity or a general API protection baseline. See [GNho trial proposal](GNHO_TRIAL_PROPOSAL.md) for pending review and deployment conditions.

## Orders comparison: rate and retry limits

The separate `tools/compare_api_security.py` synthetic orders baseline applies the same local fixed-window subject and operation admission policy as the SAPi configuration, before replay checks. A subject's keys share the 60-per-60-second budget. A local mixed replay test confirms that one normal request followed by 59 identical replays exhausts that budget, and a fresh normal request under another key for that subject is rate limited. This is an observed potential false block under the fixed policy, not proof of a safe production threshold. The baseline replay protection and counters remain single-process prototypes; no distributed fairness claim follows.

The Python SDK also has an explicit opt-in `SplitBudgetMemoryReplayStore`, selected with `SecureServer(..., split_budget=True)` or the corresponding application constructor option. It bounds authenticated attempts per service and subject at 120 per 60 seconds by default and claims replay IDs under one process lock; replay and invalid requests consume that cost budget. Only a fresh, authorized, schema-valid request consumes the existing subject and operation business budget. The legacy `MemoryReplayStore` behavior is unchanged. The cost cap can itself block legitimate traffic, and message authentication occurs before this cap: transport and unauthenticated resource limits remain necessary. The opt-in store is memory-only, non-durable, and not shared across processes; other SDKs and the state service do not implement this policy. This is not a deployment recommendation or a D1 guarantee.

An identical SAPi wire request is rejected as replay, but a fresh wire carrying the same business operation reaches the handler again. Replay protection is not business idempotency. In the fixed orders create fixture, a fresh repeat returns `changed: false`; a subsequent `get` can confirm the current record, but does not prove which request created it or reconcile arbitrary side effects. After an unobserved write response, do not automatically retry a write or an `internal_error`; query the current record when meaningful and treat unresolved outcomes as unknown. Durable operation IDs, atomic result storage, concurrent retries, deletion and external side effects require a separately specified idempotency contract and implementation.

The local `reconcile_create` helper classifies a lookup as current state matching, differing, not found, or unknown. It does not assert that a particular attempt committed, provide a durable receipt, or replace an application-level idempotency implementation. Malformed lookup results remain unknown.

The Python application has a separate experimental, **opt-in** records idempotency contract. Enabling both `Records(..., enable_idempotency=True)` and `Application(..., enable_idempotency=True)` adds optional `operation_id` to record mutations and an `orders_receipt` operation for the orders collection. Existing callers without the option or field keep their previous behavior. A key is scoped by service and authenticated subject across that subject's keys; its request fingerprint includes the operation, collection, payload and relevant operation configuration. A matching retry returns the original stored result; a different request using that key returns `idempotency_conflict`. The receipt lookup returns the historical result, separate from a current record lookup, and requires the collection's write scope.

The fingerprint also binds the declared operation name and a hash of its input/output schema and scope. Identically configured transitions with different names cannot share a key. Pre-change experimental receipts do not have this binding; retries against them fail closed as `idempotency_conflict` and are not automatically migrated. Direct idempotent `Records.mutate` calls must provide the declared `operation_name` and may provide the schema/scope contract hash; ordinary calls without an operation key remain unchanged.

For supported record mutations, the mutation and receipt commit in one database transaction. A concurrent retry waits for the transaction lock, then reads the receipt; lock timeout or unexpected failure is an unknown outcome and must not cause an automatic write retry. A crash before commit rolls back both. No separate durable `in progress` row is exposed. A successful receipt is available for 24 hours; an expired key remains a tombstone and cannot be reused. The local store caps receipts and tombstones at 10,000 and fails closed with `idempotency_capacity`; it does not automatically reclaim tombstones. Backward clock movement fails closed with `idempotency_clock`. Result payloads are stored in the application database; expiry controls availability and later writes clear expired payloads, not guaranteed immediate physical deletion. Keys should be random identifiers and contain no secrets.

Local SQLite tests cover concurrent retries, process termination before commit, restart, conflict, scope, expiry, capacity and API/SAPi access. PostgreSQL concurrency, migration of an existing database, lock recovery under real deployment conditions, multi-region consistency and external handler side effects are not validated. Enabling this feature creates receipt tables and requires a reviewed migration and storage policy before deployment. The contract applies only to these records operations; it does not make arbitrary handlers or outbound side effects exactly once.

Both opt-ins are constructor-level experimental APIs and are not exposed by the existing operator CLI configuration. The synthetic replay-aware JSON baseline and SAPi variants have also been exercised with the split-budget policy; neither experiment changes a deployed service.

Unexpected handler failures are classified as `internal_error` in all three local variants. The ordinary listener represents this as HTTP 500; SAPi returns its encrypted error over HTTP 200. An HTTP status comparison alone is not semantic equivalence. The orders variants share the same application and records code, so their fixtures do not establish independent implementation parity or complete normal-function coverage.
