# GNho comparison trial — review draft

The target is the owner's `https://gnholabs.com`. No request is sent by this proposal. The Site source and deployment configuration have not been received, so route names, bindings and integration points below are proposed contracts, not an applicable patch. The Site owner must review the actual patch, migration and stop controls before any deployment or active trial. No other host is in scope.

## Proposed integration

Keep the existing Site handler authoritative. At a trusted point where the server's existing `request_id` is available, a bounded observer may submit an eligible request to an isolated evaluator. The observer must not await evaluation on the response path. A full queue, timeout, malformed input or evaluator failure drops the observation and increments a bounded counter without changing the Site response. The exact hook, ID ownership, asynchronous lifetime and reliable loss accounting must be checked against the real source and runtime. An in-memory queue alone loses work on isolate shutdown and cannot establish completeness.

The evaluator owns two isolated dummy targets: a conventional API with authentication, schema validation, authorization and bound queries; and an actual SAPi implementation with corresponding business rules. It must not use production customer records, production workbench user input, production keys, or the Site's existing business handlers. Equivalent authenticated business operations use separately encoded protocol messages; record them as semantic comparisons, not identical bytes. Unauthenticated raw input may be offered to both protocol gates only within the documented body and metadata limits. A production SAPi ciphertext tested with an isolated key cannot demonstrate whether its original production key was valid. External URLs, XML external entities, shell commands and dynamic SQL are never executed. Unavailable, unsafe, truncated or transformed input is explicitly recorded with its relation and measurement limit; it is not counted as a pass or a blocked attack.

Persist a source observation and comparison results under the source's server-generated ID, with source time, input classification and collection/loss status; per-variant configuration and version; processing stage and reason; response class; dummy DB state before/after; measured duration; and observed or unmeasured side effects. Raw request bodies, query strings, tokens, addresses and credentials are excluded from durable output. The separately authorized trial data store must be isolated from existing Workbench users and tables. Do not rely on an IP address as a unique client: the platform may supply a gateway address. Storage writes must be bounded and failure-isolated, and reports must show missing pairs, drops and unknowns.

## Self-test versus external traffic

Run a separate, explicit self-test mode against only the trial routes, with an owner-controlled test identity and generated run UUID, individual request UUIDs and exact UTC start/end times. An authenticated server-side marker identifies the run; a caller-supplied header alone is not sufficient evidence of origin. The marker is recorded with each request and result, and trial traffic is excluded from any external-attack aggregation by an explicit verified classification. Do not modify the existing read-only monitoring automation. Label unverified markers as unknown, not self-test or external attack. Avoid storing a reusable marker secret or token in evidence.

Initial proposed ceiling for review: one active run, one in-flight request, at most 30 HTTP requests per run, at most one request per second, 8 KiB captured body, a short fixed deadline, and a bounded queue and database size. Counts include setup and both comparison variants; the owner may choose lower values. The exact caps and concurrency enforcement must be implemented server-side, tested across instances and confirmed against existing Site quotas before use. Prohibit retries of an uncertain mutation; reconcile its dummy state first. Abort on unexpected production-route access, any non-dummy write, source identity ambiguity, queue saturation, unexpected latency or error increase, inability to record outcomes, capacity limit, or owner stop. Disable the trial route by default and provide a server-controlled kill switch. These are proposed controls, not yet enforced.

## Mixed and repeated workload

Before an active run, freeze a versioned manifest of dummy scenarios, expected result and expected complete dummy DB state, with an independently reviewed ground-truth label. Include valid create/read/update/delete and allowed workflow transitions alongside malformed transport, invalid schema, denied scope, foreign ownership, stale version and authenticated replay controls. Include equivalent valid and invalid inputs at both protocol gates when meaningful. SAPi-specific tamper tests remain SAPi-only and are not counted as a baseline comparison. Unknown infrastructure errors are inconclusive, never credited as blocked. External traffic has no assumed ground truth: record `suspicious` or `unknown` with evidence; a 404 alone is not an attack label.

Use a recorded seed and deterministic ordering to interleave normal and abnormal cases. First validate with the one-in-flight ceiling above; a reviewed later phase may use bounded concurrency only after explicit capacity and latency limits are chosen and a local stress test verifies isolation. Repeat finite runs over a longer observation period with per-window and total budgets, a cool-down, and operator-visible stop controls. A run's request count, planned versus actual mix, omissions, self-test marker, source and request IDs, timestamps and source/fixture versions must be recorded. There is no background scheduler in this proposal; consider one only after the real connection and execution have been verified and separately coordinated.

Report normal rejections as potential false blocks and abnormal successful effects as potential misses only where a defined test oracle applies. Also record per-variant result and state discrepancies, latency distributions and deadlines, error and loss counts, dummy DB integrity and observed/unmeasured follow-on effects. Distinguish route/configuration differences from security behavior and avoid converting these results to a general protection score. Use a separate control for existing Site availability and abort on threshold violations; set objective thresholds from an approved baseline before running, not after seeing results.

## Schema, deployment and rollback to review

Inspect the existing source, binding declarations and migration journal before choosing names. Add only bounded, schema-only, additive trial tables and indexes in a new migration; do not rewrite existing migrations or create tables at request time. Version the trial schema and document retention, cleanup and ownership. Do not backfill or seed production user data. A failed Sites deployment can still have applied its migration, so verify the actual migration state before retry or rollback. Prefer disabling the isolated routes and restoring the previous Worker version while leaving additive trial tables inert; deletion or data cleanup requires a separately reviewed retention decision. Local preview and hosted D1 are distinct. The Sites storage instructions require one statement per `prepare()` and `batch()` for multiple statements; transaction, concurrent admission and D1 consistency claims must be verified in the selected runtime rather than assumed.

Before requesting deployment review, produce a source-specific diff, exact schema migration and rollback steps, explicit route and identity configuration, evidence of no change to existing routes, bounded load and failure tests, and a redacted query/report example. Run local tests with fake inputs and dummy data, including failure of storage, queue exhaustion, unknown request identity, malformed wire, duplicate IDs, concurrency and explicit stop. Assess key provisioning and durable replay/rate/usage reservation across isolates. The current Node VM and Python tests do not establish those properties in the actual Worker.
