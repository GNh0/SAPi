# D1 replay and admission: exclusive service mode

The D1 store requires `mode: 'exclusive'` and a fixed trusted service, policy version, operation map and capacity settings. Use a separate D1 database for each service; no shared multi-service reservation mode is implemented. Constructing without explicit exclusive mode fails. Earlier releases allowed shared tables and are not configuration-compatible with this mode. A singleton owner and database triggers enforce one replay-schema owner, immutable policy, namespace ownership and claim/rate row caps. These checks do not prove that unrelated app tables or direct writers are absent. Configure a dedicated D1 binding, restrict its writers, and drain all older clients before transition. Do not take a service name or policy from an incoming request.

For a new database, install `sdks/javascript/src/state-d1.sql` from a checkout. In an installed npm package, the SQL and migration files are packaged beside the `sapi-protocol/state-d1` module, but are not exported package subpaths: resolve the module path with `createRequire(import.meta.url).resolve('sapi-protocol/state-d1')` and locate the SQL by its sibling filename. Merely resolving or importing a module never applies SQL. An administrator must separately call `initializeExclusivePolicy(db, store)`; normal request methods never initialize, increase capacity or change policy. Initialization checks existing policy and retained rows; foreign or malformed namespace data, incompatible policy and data exceeding the proposed cap deny adoption without deletion. A successful initialization freezes the owner and policy against ordinary updates and deletion. Policy changes or quota reductions are not provided as normal operations; they require a separately reviewed administrative migration and in-flight drain. Do not drop guards or reset counters as a shortcut.

For a database with the previous policy-enabled schema, the additive `state-d1-exclusive-migration.sql` only creates owner/guard objects and changes no existing rows. Older mode-less policies do not match exclusive policy; they will not be adopted automatically. Before conversion, stop old writers, preserve a backup, inspect all existing policies and retained claim/rate rows, verify exact service identity and proposed quotas, and review a transactional administrative policy conversion. If the existing data has multiple services, invalid names, too many rows or unresolved in-flight work, stop rather than altering or deleting it. Conversion is a distinct operation and this package does not automatically perform it.

Policy and service are fixed in the constructed store, checked against the DB before each request and again in each mutation. Different versions or configurations fail closed. The last successful claim or admission does not cancel a handler if an administrator changes policy afterward; drain work and reconcile uncertain writes before any transition. A write whose response is lost may have committed. Never infer that the handler did not run solely from a lost response; use the application receipt for business outcomes.

Default SDK mode does admission before claim; opt-in split-budget mode consumes a separate per-subject replay cost budget before validation/policy and business admission. The adapter accepts custom-provider subjects without Unicode normalization or truncation, including email addresses, delimiters and controls. A subject must be well-formed UTF-16, 1–1,024 UTF-16 code units and at most 4,096 UTF-8 bytes; lone surrogates fail closed before encoding. These are adapter bounds, not SDK core subject requirements. SDK replay identity remains `(service, kid, request ID)`; subject partitions cost and business budgets and is not part of that identity. Reusing a wire is rejected. A fresh wire needs application-level durable idempotency to avoid repeating business effects.

Cleanup is explicit, service scoped and bounded to 100 expired rows per table per call. The 30-second post-expiry replay hold and the longest supported rate-window retention remain. Full tables fail closed until safe cleanup. The limits bound replay-table rows, not all DB bytes, external requests, query cost, CPU, the shared platform queue or billing. Separate service databases provide row-capacity isolation only; they are not a blanket multi-tenant availability guarantee.

Local tests use temporary Miniflare D1 databases and do not establish live Cloudflare D1 distributed behavior or a process restart. Run with an installed Miniflare module or set `D1_TEST_MINIFLARE` to its entry point. The earlier cross-service shared-capacity demonstration is historical and requires an archived local cd9d821 checkout and explicit historical test flag; that local commit is not included in the published branch history.

See [D1 Database API](https://developers.cloudflare.com/d1/worker-api/d1-database/), [D1 limits](https://developers.cloudflare.com/d1/platform/limits/), and [read replication](https://developers.cloudflare.com/d1/best-practices/read-replication/).

### Legacy policy conversion rehearsal

`tests/test_d1_transition.mjs` shows a local, explicit administrator-only D1 batch after the additive migration and after old writers are drained. The first statement conditionally updates the one policy only if its service, version and complete old configuration equal reviewed values. The second inserts the singleton owner only when `changes()=1` from the preceding update and the resulting policy exactly matches the intended exclusive configuration. The owner trigger rejects foreign/malformed retained rows or counts above the new caps; D1 rolls back the batch if that statement errors. Confirm one changed policy row and one created owner, then independently read and compare the owner, policy and preserved row counts. A zero-row result is not successful conversion. If acknowledgement is lost, stop and reconcile the actual rows; never infer rollback or delete retained records. A repeat with the same old configuration changes zero rows after a successful conversion.

This test is a rehearsal, not an approved production migration. Derive and verify the complete old and new canonical configuration from actual trusted server settings, review all rows and competing policy records, and prepare backup and operational rollback before any deployment. A populated multi-service DB cannot safely become one exclusive service in place; allocate separate databases and separately review migration of retained state instead of deleting it.

The database guard validates UTF-8 and canonical tuple bytes with bounded recursive SQL. Work increases with subject length, and administrative checks over many retained rows can be expensive. No local test establishes production CPU or billing limits. An existing database with the earlier NAME-only exclusive triggers needs the separately reviewed `sdks/javascript/src/state-d1-subject-migration.sql`; its exact preflight, transactional batch, reconciliation and rollback requirements are in `sdks/javascript/src/state-d1-subject-migration.md`. Nothing silently modifies existing triggers or rows. The owner protects this replay schema, not unrelated tables, arbitrary direct writers or physical ownership of the database.
