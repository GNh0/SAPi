# 인증서 파일 없이 시작하는 방법에 대한 검토

목표는 개발자가 인증서 발급, 파일 배치, 환경별 경로 설정과 갱신을 직접 관리하지 않고 SAPi를 사용할 수 있게 하는 것입니다. 현재 지원되는 기능이 아니라 구현 전 설계입니다.

현재 State Authority는 HTTPS/mTLS와 인증서 fingerprint로 관리·서비스·클라이언트 역할을 구분합니다. 초기화 시 CA와 인증서 파일을 만들고, 각 실행 환경에 CA와 개인 키를 안전하게 전달해야 합니다. 메시지 키는 발급 후 사용량과 만료를 기준으로 자동 회전하지만 최초 인증서 배포·등록과 인증서 교체까지 자동화된 것은 아닙니다. 정적 키와 메모리 저장소를 쓰면 설치는 단순해지지만 키 배포와 다중 인스턴스 상태 문제가 남습니다. [상태 서비스 운영](STATE.md)과 [보안 모델](../spec/SECURITY.md)에 현재 계약이 있습니다.

우선 검토할 방식은 실행 플랫폼이 관리하는 HTTPS와 이미 검증된 워크로드 신원을 사용해 관리 서비스를 호출하고, SAPi 키 발급·보관·회전은 서비스 측에서 자동 처리하는 것입니다. 개발자가 볼 설정은 서비스 선택과 권한 승인 정도로 줄이는 것을 목표로 합니다. 플랫폼이 신원과 TLS를 실제로 제공하는지, 해당 신원을 어떤 서비스·주체·scope에 연결할 수 있는지 먼저 확인해야 합니다. 현재 mTLS 전용 State Authority에 그대로 연결되는 기능은 없습니다.

1. 운영자가 신뢰할 플랫폼과 허용할 서비스·주체·scope를 한 번 등록합니다. 배포 환경은 플랫폼의 기존 인증된 신원을 사용해 짧은 수명의 접근 권한을 얻습니다. 사용자가 발급받은 개인 인증서 파일을 설정에 넣지 않습니다.
2. 신뢰된 채널에서 권한을 검증한 뒤 해당 주체에만 SAPi 키와 재전송·사용량 상태를 제공합니다. 클라이언트 SDK는 활성 키 선택, 만료 전 회전 경합과 폐기 후 실패를 처리합니다. 이미 수행 중인 업무의 취소나 정확히 한 번 실행은 별도 업무 계약이 필요합니다.
3. 플랫폼 권한이 폐기되거나 서비스가 중지되면 새 키 조회·예약이 거부되도록 하고, 누출·장애 시 폐기와 복구를 시험합니다. 감사 기록에는 신원과 결정만 남기고 키나 토큰을 남기지 않습니다.

다른 선택지는 플랫폼이 mTLS 인증서를 발급·갱신하고 런타임에 주입하는 것입니다. 기존 State Authority 계약을 더 잘 보존할 수 있지만 그 플랫폼이 자동 발급과 안전한 전달을 실제로 지원해야 합니다. 반대로 오래 사는 공유 키를 개발자 설정이나 브라우저 번들에 직접 넣는 방식은 인증서 파일 대신 비밀 관리 부담을 옮길 뿐입니다. 브라우저에 장기 공유 키를 넣거나 인증서 검증을 끄고 해결하지 않습니다. 일반 HTTPS와 SAPi 중 어느 쪽도 실패 시 다른 쪽으로 자동 우회하지 않습니다.

GNho에서는 실제 Worker의 플랫폼 신원, 관리형 TLS, 비밀 저장과 수명 관리 기능 및 비용을 확인한 뒤 별도 검토가 필요합니다. 승인된 소스와 배포 경로가 아직 없고, 자동 초기화·회전·폐기 경로는 구현하거나 시험하지 않았습니다. 새 키나 지속 접근 권한은 발급하지 않았습니다. 먼저 로컬 모의 신원으로 발급·만료·회전·폐기·장애·동시 요청을 검증하고, 이후 허용된 환경에서 실제 플랫폼 계약을 확인해야 합니다.
