# Historical cd9d821 shared-capacity design: not implemented

At commit cd9d821 the store counted every claim or rate row in shared tables against the calling service's configured capacity. The local Miniflare counterexample in `tests/test_d1_cross_capacity.mjs` configures two independently registered services A and B with claim and rate capacities of 2. Two distinct A claims fill the shared claim table and reject B's first claim. One A admission creates two rate rows and rejects B's first admission; the SDK returns rate_limited with zero handler invocations. This is row-capacity interference, not proof of distributed D1 behavior. The cd9d821 implementation and defaults did not guarantee service or tenant capacity or availability isolation. The subsequent exclusive mode requires one service per database; it does not implement the shared reservations described below.

A candidate strict-reservation design, requiring independent review before implementation:

* Register each trusted, server-owned service explicitly with separate claim and rate row quotas. In one administrative transaction enforce `sum(claim reservations) <= global claim cap` and `sum(rate reservations) <= global rate cap`, counting active and draining reservations. Reject unregistered services and concurrent registrations that exceed either cap. The caller must not select a service or allocate capacity from a request.
* Maintain per-service and global usage transactionally with inserts and deletes, preferably in database triggers in the same transaction as the row change. Existing-key renewal does not increment counts; a deletion decrements once. Atomically reject any new row if its service quota or the corresponding global cap would be exceeded. Distinct service columns and composite unique keys must preserve the SDK's service/kid/request-ID identity and rate tuple encoding. The registry and row counters themselves need bounded capacities and a reconciliation procedure. Alternatively indexed per-service counts can replace per-service counters, with explicit bounded row-read costs; the global cap still needs a coherent authoritative count.
* Never permit requests to alter reservation sizes or move to a new namespace. Increase or add a reservation only through a reviewed administrative transaction with sufficient unreserved global capacity. Decrease or release only when the durable usage fits the new quota, required retention has elapsed, and in-flight or uncertain operations have been resolved. A paused/draining service retains its reservation until then. Lost administrative acknowledgements require reading the authoritative registry and reconciling a stable operation ID, not an assumed rollback.
* Transition policies by stopping entry, draining or reconciling already admitted work, then changing registry state/version atomically. Database write guards must check the registered version/state at execution; they cannot cancel a handler already admitted. The current SDK does not itself prove handlers drained, so a bounded inflight lease/receipt design or explicit operator reconciliation remains required.
* Keep current conservative TTL semantics; bounded cleanup must delete only expired rows, respect service ownership and update counters atomically. A lost delete acknowledgement is uncertain and must not trigger a second guessed counter decrement. Reconcile counters against authoritative rows before any administrative repair.

For example, a global claim cap of 10 may reserve A=4 and B=6; A's four rows cannot consume B's six reserved slots. A new service C requesting one slot must be rejected until an administrative transaction safely reduces or releases an existing reservation. Quotas represent guaranteed row slots, not additional physical storage; they can leave slots idle. Borrowing unreserved slots is a different, more complex contract and is not proposed here.

Even strict row reservations cannot guarantee multi-tenant availability: the D1 database queue, CPU, storage bytes, network, failed-request queries and billing remain shared. Denials still cost queries. A separate global DB-time execution budget can bound accepted work, but cannot impose an absolute bound on external requests or denial costs. No new schema, migration, policy or operational change is implemented by this document.
