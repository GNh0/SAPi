# Comparison harness maintenance and boundaries

This is an experimental, local evidence harness, not an operational collection service. Its fixed orders fixtures are test configuration, not a claim that all APIs have the same functions. See `AUDIT_EVIDENCE.md`, `API_COMPARISON.md` and `SHADOW_INPUT.md` for provenance, reproducibility and measurement limits.

## Responsibilities and dependencies

* `sdks/` and `services/application/` are the actual SAPi implementation. The only application change in this branch extracts its existing transport predicate; the harness must not alter core behavior to improve a comparison result.
* `comparison_common.py` owns the shared synthetic orders configuration and ordinary JSON transport predicate. Both the loopback baseline and the isolated input evaluator use this same predicate; it must stay aligned with the actual baseline listener.
* `compare_api_security.py` currently owns the loopback baseline, fixture definitions, execution and result reporting. `verify_order_parity.py` and the classification importer reuse its local test helpers. This remaining coupling is technical debt: split baseline, orchestration and storage when a stable interface and actual live integration are defined, with regression tests for each boundary. Do not reuse the loopback baseline as a production API.
* `examples/shadow/` contains an illustrative bounded observer and a separate JS SDK inspector. Neither provides an authenticated bridge or durable storage. `evaluate_shadow_memory.py` is an isolated in-process evaluation, while `import_shadow_observations.py` maps classifications to synthetic fixtures. They do not execute the same evidence and must not be merged into a single provenance label.
* Tests exercise contracts and negative controls; result reports query their SQLite evidence. A stage in these reports is inferred, not an execution trace. A sentinel digest is not a real business database snapshot.

## Storage and lifecycle

Comparison and parity now create SQLite schema version 1 and require a new path. `migrate_evidence.py --source OLD --destination NEW --kind comparison|parity` copies a recognized intact unversioned DB before a transactional schema upgrade; it never modifies the source. Migrated runs are `legacy_unverified`: missing provenance and execution completion cannot be reconstructed. Preserve the old file and producing source. This migration is limited to the two documented legacy schemas; it is not a general migration framework. Shadow tables remain unversioned and use `CREATE TABLE IF NOT EXISTS`, which does not validate an existing schema. Use a separate new database per revision. Never point these tools at a production database. Further migrations, backup, rollback and retention need operational validation before deployment.

New runs persist `running` and each observation individually, then mark `completed` only after the loop finishes. A crash leaves committed observations and `running`; this label alone does not prove the process is still alive. Query comparison with `report --db PATH` and parity with `--db PATH --report-run RUN_ID`. Partial or legacy runs cannot report an overall pass. There is no in-place resume: business state, credentials and replay context are ephemeral. Preserve the incomplete file and run again in a fresh DB; correlate the two runs externally rather than merging their results. Startup or storage failure may leave no usable database, and an uncertain write must be checked before retry. SQLite durability remains dependent on filesystem and runtime guarantees.

The isolated evaluation and classification import wrap result writes in a transaction; exceptions roll back. Repeated request IDs are marked `duplicate_unverified` by the memory evaluator because input bytes are not retained and identity cannot be established. The classification importer checks batch identity and detects conflicts. No delivery queue or automatic retry is implemented. A caller must distinguish a failed/unknown write from a committed result, check the existing ID before retry, and record loss; a retry must not silently create another observation. The example observer's bounded in-memory queue can drop entries or disappear on shutdown. No guarantee of completeness follows from its self-reported counters.

The comparison and parity loops record caught action failures as `execution_error` with a bounded category, never exception text. Report validation rejects missing or inconsistent observations; parity additionally checks an independent expected state for each step. The baseline catches unexpected handler exceptions and responds as invalid input, which can hide an internal failure from the response; the controlled fixture expectations are not a substitute for production diagnostics. Error classification and privacy-safe diagnostics require further design before live use.

## Configuration and verification

Limits, mappings and test credentials are deliberately fixed or ephemeral in these local scripts; `--repetitions` is bounded and output paths are explicit. Changes to fixture or baseline behavior change the comparison and should be reviewed with the expected outcomes and negative controls together. New runs record Git HEAD/dirty status, hashes of Python source trees and tool/test files, Python/SQLite/OS information and installed distribution versions. These are not a signed build or complete binary/environment inventory. Existing databases retain their original provenance and should be interpreted with their original revision.

Run the commands in `AUDIT_EVIDENCE.md` on a clean scratch directory. Successful tests establish only those cases and that runtime; they do not establish maintainability, production security, full API parity, Site compatibility, D1 atomicity, performance or real-traffic coverage. A live adapter needs an authenticated source, request-ID linkage, bounded asynchronous transfer, explicit loss accounting and independent failure isolation before deployment.
