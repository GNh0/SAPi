# Observed-request regression and evidence

`tools/verify_observed_requests.py` turns broad, sanitized request categories into a small deterministic suite against a disposable loopback HTTP listener. It does not ingest access logs or reproduce an actual request. It uses generated in-memory test keys, an in-memory replay store, a temporary SQLite database, and the existing orders application. No persistent credential is issued. The XML body is the harmless `<fixture/>`; no XML parser is invoked by this path. The suite never contacts the observed site or any external URL.

```text
python tools/verify_observed_requests.py --output /absolute/scratch/observed-requests.json
```

Requires the Python SDK and application dependencies (see `docs/VALIDATION.md`). The output is overwritten at the selected path. It contains fixed case identifiers, response match/mismatch classifications and bounded counters, fixed expected fixture values, not observed response contents, request wires, tokens, keys, IP addresses, personal data or raw traffic. Unexpected responses are compared but never serialized. Exit code 0 means every case passed; a case exception or mismatch produces a failure and nonzero exit. Setup failures terminate with a nonzero exit and may leave no report; if the output already exists it may still contain an older run, so check the exit code and timestamp. Store reports in a controlled scratch directory, not a public log. Do not feed real traffic into this tool.

The suite exercises path and method probes, XML content types on several routes, oversized and ambiguous framing, invalid SAPi wire, and authenticated normal, invalid schema, insufficient scope, foreign ownership, invalid state, valid transition and replay cases. Each case compares the exact response, gateway and records-handler entry counts, application-record table contents before and after, and SAPi egress connection attempts. Expected stage is the intended decision point inferred from the result and counts, not internal tracing of every branch. A failed observation is never a pass. The full records table comparison excludes replay/rate state; authentication and replay themselves can update that state. The egress hook prevents and counts only calls through `sapi.egress._connect`; it is not an OS-wide network monitor. External file reads and all other network activity are not measured. No conclusion about an XML parser or XXE behavior is drawn from rejecting an XML content type before parsing. The suite checks this implementation and its fixed cases, not live attack success, broad coverage, production configuration, HTTPS, durable replay, or PostgreSQL.

Existing `tools/verify_application.py` provides additional independent HTTP/HTTPS, managed state, multi-SDK, ownership, schema, workflow and egress checks; run the full validation commands in `docs/VALIDATION.md` as appropriate. Results should identify the source revision, runtime and omitted backends. Never publish scratch keys, databases, raw requests or private logs.

## Separate public dummy deployment scope

A public dummy is not provisioned by this suite. Before considering one, define ownership, authorization, retention and legal review; use an isolated account, network and disposable data with no path to production, restricted egress, bounded resource quotas, abuse monitoring, incident response and a controlled shutdown. Assess HTTPS, durable replay, key lifecycle and authentication, deployment-specific ingress controls, and the privacy and retention of aggregated logs. Review infrastructure and access changes separately, approve and test them in a dedicated environment, and only then make an explicit deployment decision. This local evidence is not approval or proof of readiness for public exposure.
