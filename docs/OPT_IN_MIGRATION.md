# Opt-in SAPi migration: small local proof

The illustrative `examples/migration/gateway.py` wraps one existing business function with the real Python `SecureServer` and leaves the host's existing API handler intact. It supports explicit `legacy_only`, `dual`, and `sapi_only` modes. The host maps distinct, fixed routes to `legacy` and `sapi`; neither malformed SAPi input nor an authorization, replay, handler or state failure falls back to the legacy route. Disabling the legacy route is necessary to stop clients using its separate security policy. `dual` deliberately leaves it reachable and does not upgrade its security.

This is an in-process proof, not an HTTP middleware, package feature, transparent API conversion, Worker implementation or live GNho connection. Existing authentication, authorization, data validation, transactions, idempotency, error mapping and TLS remain the host's responsibility on the legacy route. The SAPi operation requires its own scope, input/output schemas, policy and principal-aware handler. Map a trusted authenticated identity to the existing business identity; never trust a client-supplied owner. Verify that both routes enforce equivalent business authorization and transaction boundaries. Output validation follows the handler, so an existing handler must ensure invalid output cannot commit a mutation; this proof's echo handler is side-effect-free.

## First local call and transition

1. Install the Python SDK and dependencies using the project's [usage instructions](USAGE.md). `python -m unittest discover -s tests -p test_migration_gateway.py -v` runs the proof from a checkout. It creates ephemeral in-memory keys and replay state, and never opens a listener.
2. For an application, supply a configured `Codec`, an appropriate replay store, the existing authenticated legacy route callable, the SAPi operation name and scope, explicit schemas and policy, and a business handler accepting `(principal, data)`. These are security decisions, not a single source-code switch. Use State Authority and an appropriately shared durable state design for production; the test's static keys and `MemoryReplayStore` are not distributed state.
3. Start with `legacy_only`, configure an authenticated client key and trust boundary, then use `dual` for clients intentionally migrated to the fixed SAPi route. A SAPi client uses `codec.request(kid, operation, data)`, sends the resulting wire on the SAPi route and calls `codec.accept_response(context, response_wire)`. The test verifies that this and the legacy route call the same function and return the same normal result.
4. Check errors independently: malformed or unauthenticated wire fails at the SAPi boundary; authenticated forbidden or invalid operations return a protected error. Host HTTP status/error mapping is not specified by this example. No automatic retry or downgrade is performed. An uncertain mutation outcome needs application-specific reconciliation before retry.
5. After migrating and verifying clients, explicitly select `sapi_only`; a request to the old route must be rejected by the host. Rollback to `dual` or `legacy_only` is an explicit deployment/configuration decision that restores the legacy route's original security exposure. Coordinate client versions, keys and state, preserve evidence and test rollback in the target deployment.

## Alternatives and limits

Separate routes make protocol selection and rollback visible but require client changes and an explicit legacy retirement plan. Transparent negotiation would preserve more client code, but risks accidental downgrade and hidden policy differences; it is not implemented. A framework-specific middleware could reduce integration effort, but must first define HTTP body limits, error mapping and lifecycle for that framework. The existing declarative `sapi-application` is a better fit for new supported collections; it is not an automatic wrapper for arbitrary existing APIs. A Worker adapter needs a separately validated JavaScript implementation, runtime packaging, distributed state and trusted key setup.

The local tests cover explicit modes, normal shared-function behavior, malformed messages and scope denial; they do not prove HTTP integration, every legacy endpoint, independent authorization equivalence, durable state, migration of real data, operational rollback or production readiness. Live comparison still requires authorized Sites source access and an isolated request bridge.
