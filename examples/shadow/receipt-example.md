# Synthetic receipt example

This local example demonstrates a receipt and a business effect committed together, output validation before the write, ownership checks, and a bounded key tied to the subject and normalized operation. It uses invented in-memory identities and isolated SQLite fixtures. It is not an authentication system, a production database schema, or a deployed service.

The operation key is globally unique in this example. A different principal cannot independently reuse the same key. A fresh wire retry can call the handler again, while the committed business effect remains at most once. A lost response after commit must be resolved by receipt lookup; absence of a receipt at one instant does not prove that an in-flight write cannot commit later. Server object replacement in the test is not a process restart, and this example does not test key rotation or distributed replay.

Run with Node.js 22.13 or later (the test requires the experimental node:sqlite API):

    node tests/test_receipt_contract.mjs

The test uses an in-memory SQLite adapter. It is not evidence of distributed D1 concurrency or production response delivery guarantees.

## Three-boundary local comparison

Run `node --experimental-sqlite tests/test_contract_comparison.mjs` from the repository root. `contract-comparison.mjs` reuses this exact receipt/business implementation and SDK schemas. The independent case catalog is `tests/contract-comparison-oracle.mjs`; it fixes expected responses, handler counts, business effects and receipt deltas before execution.

The existing conformance workflow runs this comparison and the receipt regression on Node.js 24 in both its Linux and Windows verify jobs. Their shared CI step has a two-minute limit; the fixture's cooperative checks are separate from that runner-enforced step limit.

The fixture compares an ordinary JSON API with an already authenticated synthetic session, a JSON API with an additional HMAC over its exact request body, and the real SAPi SDK. All three enforce scope, ownership, strict input validation, the same replay/rate store policy, precommit output checks and the same atomic business receipt. The ordinary API is a capable baseline. An authenticated, protected transport is assumed for its session and JSON response; this fixture has no HTTP listener and does not implement or validate real session authentication or TLS. HMAC fixture keys and SAPi fixture keys are independently generated in memory, never persisted or printed. This comparison is about business-contract parity under those assumptions, not a measurement of three deployed API stacks or an authentication penetration test.

The common sequence has 16 fixed cases and 11 recovery controls per variant, plus two groups of eight concurrent attempts: 129 calls total (43 per variant). Those groups distinguish replay of one request (one handler entry) from fresh requests sharing a business key (eight handler entries, one business effect). Mode-specific integrity controls add 18 calls, making the baseline run 147 calls: ordinary 43, hardened 51, SAPi 53. Each fixture has a cap of 160 executions, 16 mutation constructions and 256 synthetic receipt lookups. The business input limit is 7900 UTF-8 bytes and the JSON envelope limit is 8192 bytes. A baseline plus five source mutation runs has an execution upper bound of 960 calls. A 10-second cooperative check per fixture is not a hard timeout or verified process isolation. Each variant has its own in-memory SQLite and a replay store retained throughout that sequence; a request-local SAPi server wrapper attributes handler entries without racing global state.

The serial denominator per variant is 27: 16 normal controls (five original cases and 11 recoveries), two unauthorized cases, two schema-invalid cases, one unsupported operation, four injected failures, and two business-key conflicts. These categories replace the earlier misleading `invalidInputs` aggregate. Normal controls require an accepted response and exact business semantics; normal rejection, uncertainty and semantic mismatch are reported separately. The four injected failures are precommit output failure, precommit database failure, lost commit acknowledgement and dropped response. They are deliberately separate from normal controls. Conflicts retain the current conservative uncertain response while the database oracle requires no additional effect or receipt. These bounded cases do not establish population false-positive or false-negative rates.

The independent oracle checks all item owners and values, each receipt's key/owner/item/operation/normalized content/result, and both principals' receipt visibility after every serial case. It does not derive expected state from the business implementation or from agreement among the three modes. Common final state requires 17 effects and 17 receipts per variant before mode-specific workloads. Two concurrency groups independently require one effect and one receipt; only the identical-wire group requires one handler entry.

Four fixed request mutations exercise the HMAC and SAPi verification layers: body/ciphertext tampering, signature/tag corruption, key-label substitution and a request authenticated using the other principal's key. Each must be rejected before handler entry with no effect or receipt, followed by a fresh normal recovery. HMAC also binds the synthetic session principal to its signing-key identity. The ordinary JSON fixture records these request-integrity controls as `not_applicable`, requiring external authenticated protected transport; it is not assigned a weakness score for lacking a protocol cryptographic envelope. Ordinary and HMAC response integrity similarly require external protected transport. A corrupted SAPi response tag is tested separately: the committed effect remains one, delivery is uncertain, authorized receipt lookup reconciles it, and a fresh-wire business retry adds no effect. This is local fault injection, not a live network-loss experiment.

Five fixed in-memory source mutation controls must fail an independent assertion: double business effect, shared authorization bypass, receipt-owner leakage, ordinary scope bypass, and HMAC verification bypass. The actual implementation source is imported with one bounded mutation at a time, without changing source files. Import/runtime crashes do not count as detected contract defects. All five are detected by the local test; this is a narrow mutation check, not exhaustive coverage.

Latency is a local descriptive observation over the 27 mixed serial cases: preparation is measured separately from execution, business writes and response consumption. SAPi execution includes response decryption and request binding; other responses are local objects on an assumed protected channel. No real account authentication, session validation, TLS, credential theft, network/D1 latency, distributed state, key rotation, complete stack restart, live response loss, performance ranking or security superiority is established. Existing SDK corpus and receipt tests remain separate evidence for their documented scopes.
